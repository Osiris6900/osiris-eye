# Audit: #416 packages 45, 47 and 48

Paper-only. `live_trading_authorized` is unchanged and there is no live order path.
Package 44 (event-sourced order/decision journal) is the projection the durable
book already uses. This note records what the code and tests show, then the gap
this change closes.

The canonical book is `services/quant-api/src/osiris_api/paper_execution.py`.
The opt-in Alpaca **paper** transport is
`services/quant-api/src/osiris_api/control_plane/broker.py`. It is not wired to
an order route. `Connections.test_broker` is a read-only account probe and does
not submit.

## 45 — Order management lifecycle

Durable states are `new` (not stored), `accepted`, `partially_filled`, `filled`,
`cancelled` and `rejected`. `_ORDER_TRANSITIONS` / `order_transition` reject any
other move with `invalid_order_transition`.

| Move | Where | Idempotency |
| --- | --- | --- |
| new → accepted, rejected, or accepted → filled | `submit_paper_order` | Same client id and economics replay; a different payload is `idempotency_key_conflict` |
| accepted / partially_filled → partial or filled | `apply_paper_fill` | Client fill id replays; overfill and a price through the limit stay open |
| accepted / partially_filled → cancelled | `cancel_paper_order` | A second cancel is `cancel_replay` and does not write another cancel |
| terminal → fill or cancel | both | Audited `invalid_order_transition`, no cash or position change |

A crash before commit rolls back. Restart reads the same cash, positions, P&L
and audit chain. Open buys reserve cash and open sells reserve shares, so a
second working order cannot spend the same balance. Fills re-check the kill
switch, feed freshness and current limits. `LIVE_EXECUTION_ENABLED` is `False`.

Evidenced by `services/quant-api/tests/test_paper_order_lifecycle_179.py`
(transition table, partial fills, cancel replay, illegal cancel/fill, crash
rollback, fill/cancel race, kill switch, stale fill, reserved cash, HTTP
lifecycle) and `services/quant-api/tests/test_paper_journal_projection.py`.
`paper_order_guard.py` is a separate in-memory gate. It is not the durable book.
`phase11_systems.simulate_order_lifecycle` only checks one caller-supplied
snapshot. It does not persist a transition.

The in-memory guess that the durable machine is missing is not what the code
does. These lifecycle pieces are still absent on that book:

- No `expired` state and no time-in-force. A resting order stays fillable on a
  later day when the fill's own timestamp is fresh.
- No replace. Changing price or size is cancel plus a new client id. There is
  no `pending_replace` and no link between the two orders.
- The Alpaca day-order snapshot set listed `done_for_day` but did not treat it
  as terminal. Reconciliation could move that order back to `accepted`,
  `partially_filled` or `pending_cancel`, including an extra in-limit fill.
  `validate_broker_snapshot` requires `time_in_force=day`, so that status is
  the end of the session.

## 47 — Independent pre-trade risk gateway

`risk.check_execution` and `pretrade_gate` fail closed. Defaults are kill switch
on, feed stale, and risk service unavailable. Approval requires the opposite,
then order, position, gross and daily-loss limits. The Rust kernel in
`crates/risk-kernel/src/lib.rs` implements the same decisions. Shared vectors
are `tests/risk_conformance.csv` and `tests/risk_execution_conformance.csv`,
checked by `services/quant-api/tests/test_risk_conformance.py`,
`test_risk_execution_conformance.py` and the kernel's `cargo test`. Python
reason strings are mapped onto the Rust reason codes in those tests.

The durable submit and fill paths call `check_execution` inside the write
transaction. Position, gross and realized P&L come from the ledger. The
persisted kill switch cannot be cleared by the request flag. A float approval
is vetoed by `_decimal_risk_reason`, which includes adverse unrealized loss
(`DAILY_LOSS_BASIS = realized_plus_adverse_unrealized`). An exception from the
risk call becomes `risk_service_unavailable`. Tests:
`test_paper_risk_acceptance_179.py`, `test_paper_execution_controls_179.py`,
`test_paper_unrealized_daily_loss_179.py`, `test_paper_marked_exposure_179.py`,
`test_risk_boundary_regressions.py`.

The gateway is not a separate process. The order path calls the Python function
directly. Nothing in the order path calls the Rust crate. Agreement is the CSV
contract, not a runtime check.

Other gates are weaker and do not replace that path:

- `paper_execution_gate.authorize_paper_order` uses `check_order` and does not
  see gross exposure or side. `ghost_trade_router` returns a paper decision and
  does not submit.
- `AlpacaPaperBroker.submit` takes caller-supplied position, gross, daily P&L,
  kill switch and freshness, forces `risk_service_available=True`, and applies
  an exact decimal veto for notional, position and gross only. It does not
  repeat the paper book's exact daily-loss veto. The method is library-only
  today.
- `paper_workflow.evaluate_paper_workflow` can approve an intent, and
  `submit_approved_workflow` still rechecks the ledger before a fill.

Sells do not re-apply the daily-loss limit after the pre-trade gate. A sell
must be within the current position and gross, so it reduces inventory.

## 48 — Post-trade ledger / broker reconciliation

`_reconcile_breaks` replays fills into cash, realized P&L, positions and
unrealized P&L, then checks order residue (state, filled quantity, leaves,
fees, limit price, orphan fills) and the v2 journal projection. Depth plans
are included when present. A break raises `reconciliation_break` and blocks
new orders and fills. `reconciliation_report` returns expected versus recorded
fields, mismatches, open orders and `passed`. Recording a mismatch appends one
`reconciliation_mismatch` audit event. Admin reads use the same break list
(`control_plane/accounting.py`).

Evidenced by `test_paper_order_lifecycle_179.py` (cash and unrealized tamper),
`test_paper_journal_projection.py`, `test_durable_paper_ledger.py` and
`test_paper_accounting_acceptance.py`.

That check is the ledger against itself. It does not load an external paper-broker
position, cash or fill book. `POST /portfolio/ledger/reconcile`
(`phase11_systems.reconcile_ledger`) and `POST /paper/trading/reconcile`
(`phase8_systems.reconcile_paper_trades`) score caller-supplied floats and can
return `new_risk_allowed` or `reconciled` without reading the durable book.
Open-order reservations are enforced on submit and are not a broker-cash break
in the report.

`AlpacaPaperBroker.reconcile` refetches by client id and
`validate_broker_snapshot` binds the snapshot to the authorized order: symbol,
side, qty, limit, `type=limit`, `time_in_force=day`, unknown states, fill
regressions, terminal freezes, and incremental prices that hide an out-of-limit
print. Tests: `services/quant-api/tests/test_control_plane_broker.py`.
`cancel` sends DELETE and does not consult that snapshot.

## Gap ranking

1. **Closed here.** A day order in `done_for_day` could be reconciled back to a
   working status or a larger fill. Same-status replay and
   `partially_filled` → `done_for_day` stay legal.
2. Canonical paper orders have no expiry or time-in-force, so a resting order
   never becomes `expired`.
3. No replace on the canonical book, and broker `cancel` does not refuse a
   terminal snapshot.
4. Risk decisions on the order path are in-process Python. The Rust kernel is
   not invoked there. Broker `submit` still trusts caller-supplied risk context
   and skips the exact daily-loss veto.
5. Reconciliation does not match the durable ledger to a paper-broker cash,
   position and fill book. The phase 8 and phase 11 reconcile routes are
   caller-supplied.

## Change in this pull request

`done_for_day` is now in `TERMINAL_BROKER_STATES`. A later snapshot must keep
that status and filled quantity. A correction is `broker_snapshot_mismatch`
and the last verified snapshot stays. `live_trading_authorized` is not set
anywhere by this change. No broker credential, network call or live route is
added.
